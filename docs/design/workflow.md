# 処理の流れ

[DESIGN.md](../../DESIGN.md) から分割した詳細。

## 起動と終了

通常起動は次の順序で進む。

1. ログを初期化する。旧タスクが付けた引数`--scheduled-cleanup-temp`なら、掃除をせず旧タスクの削除だけを試みて、UI・自己昇格・多重起動ガード・Velopackを経由せず常に終了コード0で終了する（[legacy-scheduled-cleanup-removal.md](legacy-scheduled-cleanup-removal.md)）。
2. Velopackのinstall/update hookを処理し、旧ショートカットと旧PerUser版から署名済みPerMachine版への移行を試みる。
3. デバッガ未接続の非管理者プロセスを`runas`で再起動する。昇格後に単一起動mutexを取得する。管理者起動では、共有ロックを取って旧版のサインイン時クリーンアップタスクを自己移行で取り除く。ロックを取れなければ次回へ持ち越し、失敗はログへ残して画面起動を続ける。
4. Avaloniaを起動し、`App.ConfigureServices`が設定、コマンド実行、カタログ、操作コーディネーター、ViewModelをSingletonとして構成する。
5. `SettingsService`から表示言語と利用者設定を読み、`MainWindowViewModel`へカテゴリ別ViewModelを組み立てる。

終了要求時は`MaintenanceOperationCoordinator`が新規操作の受付を同期境界で閉じてから進行中操作へキャンセルを通知し、補償処理と状態再確認を含む`finally`の完了を待つ。操作がゼロでも先に受付を閉じ、キュー済みの状態再読込を開始させない。設定保存キューをflushし、DIコンテナとログを閉じてからプロセスを終了する。

## メンテナンス操作のモデル

`MaintenanceActionCatalog` の Action / BatchSetting / Toggle / Choice を、ViewModel が排他 lease 内で実行し、結果と実状態を画面へ返す。4 型の契約、既定値・カスタム状態の表示、データの流れは [maintenance-action-model.md](maintenance-action-model.md) にまとめる。

## クリーンアップ

クリーンアップは単一項目のモデルではなく、走査と実行を分けた専用フローで扱う。`CleanupScanService`が規則データを走査して項目別の件数とサイズを返し、利用者の選択後に`CleanupRunService`が、走査結果が現在のもの（世代・設定が一致）であることを確認して選ばれた規則だけを実行する。走査は何も変更しない。実行は確認（実行中の製品の終了、受信ファイル類の再確認、推奨外の警告）を経て、サービスの停止と復帰を`finally`で補償し、成功・`Partial`・`Failed`・`Skipped`・キャンセルを規則ごとに集計して実績へ反映する。高度なクリーンとスリム化も同じ「走査→選択→確認→削除→実績」で、スリム化の前には復元ポイントを作る。詳細は[cleanup-design.md](cleanup-design.md)を参照する。

## 未接続デバイス管理

未接続 PnP デバイスは複数項目の選択・確認・逐次削除を伴うため、`MaintenanceActionCatalog` の単一項目モデルではなく専用フローで扱う。`DeviceCleanupViewModel` が一覧、選択、二段階確認、進捗と結果集計を担当し、OS 操作はCoreの `IDisconnectedDeviceService` 境界へ委譲する。

`WindowsDisconnectedDeviceService` は SetupAPI から接続中 ID 集合とインストール済みデバイスを列挙し、その差をソフトウェア／仮想デバイスも含めてUIへ返す。削除時は利用者が選択した対象が再接続されていないか再列挙し、未接続のままならNewDevの `DiUninstallDevice` を呼ぶ。結果は削除済み、既に不在、再接続、失敗と再起動要否に正規化され、ViewModelが再列挙後の一覧と集計表示へ反映する。

削除対象を開く処理やアンインストールAPIが失敗した場合は、新しいSetupAPI情報セットで同じInstance IDの存在を再照合する。不在を確認できた場合だけ、削除試行前なら「既に不在」、試行後なら「削除済み」へ補正する。エラー番号だけで成功とせず、まだ存在する場合や再照合できない場合は元の失敗を保持する。削除結果を確定するため、この再照合はキャンセル後も完了させる。

「未接続デバイスなし」は列挙が成功して空だった場合だけ表示し、初期状態・キャンセル・列挙失敗を空の成功結果として扱わない。

## インストール済みアプリの更新

`WingetUpgradeAction`はwingetソースのexportがMicrosoft公式の既定設定と一致することを確認し、更新候補を一覧取得する。表が安全に解析できなければ全体を中止する。候補ごとに公式カタログを完全一致IDで照会し、1件のID一致、インストール済み表示名との整合性、Nightly・Betaなどの更新チャネル一致を確認してから、`--id --exact`で逐次更新する。IDだけではwingetの誤った紐付けによる別アプリ・別チャネルへの更新を防げないためである。名前の表記ゆれは許容するが、確認不能な候補は除外し、残りの候補を続行する。

各候補の成功・失敗・除外と終了コード（10進数・16進数）、標準出力・標準エラーの要約を結果、進捗、ログへ送る。出力から制御文字とANSIシーケンスを除き、意味のある末尾6行を抽出する。各行240文字、ストリーム要約600文字を超えた場合は切り詰めて省略記号を添える。インストール方式の不一致では発行元の公式インストーラーで更新方法を確認する案内を添える。

昇格側のwingetが終了コード`0x8A15007D`（ユーザースコープのportableを管理者コンテキストから操作できない）を返した候補だけ、`UnelevatedCommandExecutor`の厳格設定（`CreateForCurrentUserTree`）で、同一利用者の非昇格wingetを1回だけ再試行する。他の終了コードや別の失敗は再試行しない。再試行を開始できなければその候補を失敗とし、通常権限のターミナルで同じ更新コマンドを実行するよう案内する。終了コード`0x8A150014`はwingetが自動更新の対象外と判断した候補であり、「自動更新の対象外」として別に集計し、失敗に数えない。

失敗・除外・対象外のすべてが0件なら`Success`、成功が1件以上、または失敗が0件なら`Partial`、それ以外は`Failed`を返す。安全上の除外・自動更新の対象外と更新失敗を別に集計することで、意図的に見送った候補を失敗と混同しない。

## 使用中キャッシュの起動時再試行

固定 5 対象の削除予約を利用者別の保護キューへ保存し、専用コンソールが現在利用者の権限で次回起動時に再試行する（最大 3 実行・7 日）。対象の再構成、タスクの検証、期限と権限の境界は [reboot-cache-retry.md](reboot-cache-retry.md) にまとめる。
