# OS操作の境界

[DESIGN.md](../../DESIGN.md) から分割した詳細。

## OS操作の境界

`ProcessCommandExecutor`は外部コマンド名を`SystemProcessResolver`で信頼済みの完全パスへ解決し、作業ディレクトリをSystem32へ固定する。`JobProcess`は子プロセスを停止状態で生成し、`ProcessJobTracker`が子ごとの独立したJob Objectへ登録してから再開する。WindowsAppsのwingetなどが生成時から別のJobに属していても、既に登録した他の子のJob階層と競合しないためである。登録・再開に失敗した子は停止し、Win32エラーと登録失敗時の親子のJob所属状況を診断へ残す。Jobハンドルはアプリ終了まで保持し、KILL_ON_JOB_CLOSEで孤児を終了する。キャンセル時はプロセスツリーを終了する。

出力は厳密なUTF-8を優先し、途中で切れた末尾だけが不正ならその末尾を除いて再解釈する。それでもUTF-8でなければ現在のカルチャのOEMコードページ（日本語ではCP932）を使い、コードページを取得できない場合はLatin1へ代替する。進捗は`\r` / `\n`区切りで通知する。MMAgentなどの失敗診断は`CommandFailureDiagnostic`に集約し、終了コードを10進数・16進数で示す。標準出力・標準エラーは各末尾8192文字を処理し、Bearer値・URLの認証情報・代表的な秘密値フィールドを伏せる。制御文字を除いた各600文字を上限とし、切り詰めた要約には省略記号を添える。

利用者セッションで行うShell操作は`UnelevatedCommandExecutor`へ分離する。直接生成する経路では同じ停止状態でのJob登録を使うが、Explorer broker経由では既に起動したプロセスを登録するため、登録失敗はログへ残す方式である。wingetの更新でユーザースコープのportableを昇格側から操作できない場合（終了コード`0x8A15007D`）に限り、厳格設定の`UnelevatedCommandExecutor`（`CreateForCurrentUserTree`）で非昇格のwingetを再試行する。昇格プロセスとExplorerの利用者SIDが一致することを必須とし、取得できない場合や不一致の場合は起動しない。この設定ではExplorer brokerへ進まない。この設定の起動方式は、Explorerのtokenを`TOKEN_ADJUST_DEFAULT`(0x80)と`TOKEN_ADJUST_SESSIONID`(0x100)を加えた権限で複製したprimary tokenによる`CreateProcessWithTokenW`（失敗時`CreateProcessAsUserW`）とする。昇格実機で、この2権限が無い複製tokenは`CreateProcessWithTokenW=Win32 5`・`CreateProcessAsUserW=Win32 1314`で起動できず、2権限を加えると起動できた（MAXIMUM_ALLOWEDとExplorerを親プロセスにする方式でも起動できたが、権限が最小で済む前者だけを採用した）。停止状態で生成した子は、再開前に、実行パスが想定の`System32`の`powershell.exe`であること、セッションがExplorerと同じこと、整合性レベルがmedium以下で非AppContainerであること、`TokenElevation`が0（非昇格）であること、利用者SIDが現プロセスと一致することをすべて満たす場合だけJobへ登録して再開する。1つでも満たさなければ子を終了して失敗とする。起動失敗の文には、起動方式・Win32番号・呼出し元プロセスのJob所属を含める。Quick AccessとExplorer broker経由の既存経路の権限と手順は変えない（複製tokenの追加権限・再開前検証は厳格設定だけに適用する）。wingetは`SystemProcessResolver`の絶対パスで起動する。起動した非昇格PowerShellは子ごとに独立したJob Object（`KILL_ON_JOB_CLOSE`）へ停止状態で登録し、厳格設定だけ、取消・タイムアウト・ルート（PowerShell）終了のいずれの後も、そのJobを`TerminateJobObject`で終了する（Job終了の失敗はログへ記録する）。wingetは実測でJobに入らないため、取消・タイムアウト時の停止は親PIDからのプロセスツリー終了が担う。アプリが強制終了された場合はJobハンドルが閉じ、OSがJob内のプロセスを終了する。再試行側が書く結果ファイルは非信頼入力として扱い、`SchemaVersion`・型・欠落・重複を検証できたものだけを結果の分類と表示に使う。パスやコマンドには使わない。残余リスクとして、実機（WindowsApps配下のwinget）では起動したwinget自体がこのJobに所属しなかったため、Jobで確実に終了できるのはPowerShellが起動した通常の子孫（pingでの確認）までである。取消・タイムアウトではルートが生存している間の親PIDからのツリー終了でwingetが止まることを確認した。非昇格PowerShellのスクリプトは、winget起動後の例外で抜ける場合に`finally`でSystem32の`taskkill.exe /PID <pid> /T /F`を実行して未終了のwingetをツリーごと止める（失敗しても元の結果は変えない）。ただしwingetはJobに入らないため、(a)PowerShellだけが外部から強制終了された場合と(b)Lumin4ti自体が強制終了された場合（`KILL_ON_JOB_CLOSE`はwingetまで止めない）は、wingetが残り得る。サービス操作は`WindowsServiceControl`に集約する。元から稼働中のサービスだけに停止を要求し、その全件がSCMで停止済みと確認できた場合に`FileCleanupAction`が削除を進める。元から停止中・未インストールなら操作せず、初期状態が取得不能・遷移中、または停止要求後に停止を確認できない場合は削除を中止する。SCMで稼働中の依存サービスを列挙し、存在する場合や列挙不能の場合は停止を拒否する。`net stop`は`/y`を付けず、標準入力をEOFにして確認待ちを防ぎ、停止・開始とも2分の上限を設ける。停止要求はキャンセルで途中終了させず、要求前に復帰対象へ記録する。これにより停止コマンドや照会が失敗しても、呼び出し側の`finally`で元の稼働状態への復帰を試みられる。復帰時に既に稼働中なら開始を省略し、それ以外は`net start`を実行する。開始失敗時も最大60秒間SCMで稼働への復帰を確認してから再開失敗を確定する。キャンセルされた整理でも復帰失敗は`Failed`と診断で利用者へ通知する。

ファイル整理は既知のキャッシュ、ログ、一時領域だけを対象にする。未解決環境変数、相対パス、ドライブ直下、保護対象の基点を拒否し、ジャンクションとシンボリックリンクを辿らない。使用中ファイルは保持して処理を継続する。アイコン・サムネイル・フォントキャッシュは、選択済み範囲の起動時再試行を保護キューへ登録する。アイコン・サムネイル・フォントキャッシュの整理ではExplorerを強制再起動せず、安全に削除できたキャッシュをWindowsの再起動で再構築する。パッケージマネージャーは再取得可能な保存領域を個別に許可し、npmでは`_cacache`と`_logs`だけを対象として、コマンド実行に使われる`_npx`を保持する。

`CleanupOutcome`は削除・解放容量・削除不能・再起動時削除予約・安全上の除外を集計する。削除不能の代表例は最大8件のパスと理由を保持し、例外ではHRESULTも含める。1件が1024文字を超えた場合は切り詰めて省略記号を添える。結果画面とログに代表例を渡し、画面には省略件数も表示する。大量の失敗でも診断量を制限しつつ、未処理の原因を追えるようにしている。

サインイン時クリーンアップは、画面と同じ`FileCleanupGroups`と`settings.json`の選択・除外設定を使う別エントリポイントである。登録タスクは`HighestAvailable`で動作するため、サービス停止を伴う項目もUACなしで実行できる。一方で昇格済み自動実行の差し替えを防ぐため、タスク登録時に署名済みPerMachine MSI、`Program Files\Lumin4ti\current`の固定配置、実行ファイルまでの所有者・ACL・再解析ポイントを検証する。タスク定義XMLもAdministrators / SYSTEMだけが書ける保護ストレージで一時作成し、登録後に削除する。検証できない配置ではタスクを登録しない。

タスクの状態照会が失敗した場合は、読取専用COMで不存在を確認できたときだけOFFとし、それ以外は状態不明と診断を返す。COMはUIスレッド外で実行し、開始後の呼出しを強制中断せず応答を待ってから取消を確認する。

タスク名はマシン共通の `\Lumin4ti\ScheduledTempCleanup` で、Principal と LogonTrigger の両方を登録利用者へ限定する。既存タスクの所有者は Principal のアカウント名または SID で判定し、別利用者・所有者不明なら状態を不明として変更を拒否する。照会失敗時の登録は上書きなしの新規作成だけを試し、削除は拒否する。これにより共有PCで他利用者の登録を奪わないが、利用者ごとに複数のタスクを登録する構造ではない。

スタートアップ登録とファイル関連付け候補はキャッシュ整理と混ぜず、専用アクションでレジストリを整理する。`StartupCommandParser` が完全パスへ解決でき、準備済み固定ドライブ上で再解析点を通らない実行ファイルの欠損を確認できた候補だけを削除する。複数の関連付け候補の一つでも存在または判定不能なら保持し、レジストリアクセス不能は `Partial` として可視化する。

Defender の定義キャッシュ整理は、信頼済みの最新 Platform 版 `MpCmdRun.exe` で `-RemoveDefinitions -DynamicSignatures`、続けて `-SignatureUpdate` を実行する。基本定義全体を巻き戻す `-All` は使わず、保護設定も変更しない。更新不要でも正常完了となるため、画面では削除と更新確認の結果を示し、再ダウンロードしたとは断定しない。削除失敗時も更新確認は試し、一方でも失敗すれば全体を失敗とする。削除中のキャンセル後も独立したトークンで更新確認を試す。
